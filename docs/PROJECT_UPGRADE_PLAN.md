# AI Data Analyst 项目升级方案与模型交接说明

> 编制日期：2026-09-18
> 状态：已按阶段一至阶段七实施并验收；详细证据见 `docs/UPGRADE_PROGRESS.md`。
> 目标岗位：AI 应用开发，重点为 Agent / RAG 应用开发。
> 用户意图：将现有毕业设计升级为有技术深度、可复现、可展示的简历主项目。

## 1. 用户背景与协作约定

- 用户可长期投入，不以短期赶工为目标，但仍应控制范围、分阶段交付。
- 用户基本能讲清系统流程，对设计取舍、故障边界和验证依据理解尚不深入。
- 当前用户要求是形成并执行项目升级方案，不是进行面试训练。不要在接手时继续模拟面试或要求用户回答技术考题。
- 用户准备切换模型继续优化。本文件用于保留目标、决策、实施顺序和验收要求。
- 本次仅编写方案，不代表已授权发布外网、采购服务、消耗大规模模型预算、删除历史数据或变更生产环境。
- 接手模型应根据用户后续实施指令推进；普通只读检查、可逆修改和必要验证不需要反复询问。

## 2. 项目定位与最终目标

**定位：面向业务数据的可信多轮分析 Agent 平台。**

完整业务链路：

> 接入业务数据库 → 理解指标和口径 → 多轮澄清 → 检索表结构与业务知识 → 安全执行查询和分析 → 输出可追溯报告 → 故障恢复与持续评测。

最终重点证明三项能力：

1. 正确理解并保持业务条件，包括跨轮次、跨节点的数据范围和指标定义。
2. 输出有来源、可检查的答案，并明确数据不足与系统能力边界。
3. 在模型超时、Worker 中断、重复提交等情况下维持正确任务状态和结果归属。

保留现有 Python、FastAPI、LangGraph、Vue、MySQL、ChromaDB 基础，渐进改造。多 Agent 数量、框架数量和页面数量不作为升级成果指标。

## 4. 设计原则与范围控制

1. 先正确，再泛化，再优化性能；每阶段必须有可运行产物与验收证据。
2. 业务规则由受控定义提供，模型负责理解和匹配；不让模型自行发明指标口径。
3. 区分工具、固定工作流节点和自主 Agent，文档如实描述实际实现。
4. 区分 SQL 可执行、业务答案正确、报告忠于事实三个层次。
5. 可验证的计算与规则优先由程序执行，模型评判作为辅助。
6. 评测从第一阶段积累，冻结测试集不能反复用于调参。
7. 保留失败样本和负结果，简历指标必须对应版本、数据集与实验条件。
8. 不提前承诺任意 SQL 的语义正确性、严格一次执行或无成本重复恢复。

暂不作为主线：模型微调、后训练、推理内核优化、增加预测模型种类、复杂自主 Agent 群、Kubernetes、大量数据库连接器。出现明确需求和实验依据后再评估。

## 5. 阶段一：可靠性修复与当前版本基线

### 任务

- [x] P1-01：检查仓库指令、Git 状态、运行配置说明及现有测试入口，记录基线范围，不输出密钥。
- [x] P1-02：运行适当的后端回归和前端类型检查／构建，记录环境、命令、结果和未验证项。
- [x] P1-03：复核历史缺陷，优先认证回退、结果归属、记忆隔离和业务条件丢失。
- [x] P1-04：修复取消、租约交接、旧 Worker 写入、节点错误状态和消息重复累加。
- [x] P1-05：修复报告模型名称、回测与未来期间错标，以及分析和预测范围不一致。
- [x] P1-06：整理文档入口和运行产物管理，建立可复现版本记录；提交按用户指令及仓库规则进行。

### 验收

- 无效凭证无法提升权限；不同用户无法访问对方私有结果或召回其记忆。
- 请求附带的时间、地区、人群条件在后续适用节点保持一致，无法支持时明确拒绝或澄清。
- 排队取消可进入终态；失去执行归属的 Worker 不能覆盖当前结果。
- 报告内容与实际计算一致；业务失败不记录为成功。
- 每个修复有针对行为的回归验证，避免仅检查代码字符串或实现细节。

**交付物：**当前版本基线报告、复现与修复记录、必要回归测试、更新后的历史缺陷状态。

## 6. 阶段二：业务语义与多轮分析

### 任务

- [x] P2-01：在现有 TaskPlan 上设计统一分析请求，明确指标、维度、时间字段及范围、筛选、排序、数量限制、数据源、口径版本和未解决歧义。
- [x] P2-02：建立版本化指标配置，记录名称、别名、计算规则、必要字段、关联关系、支持维度和使用限制。
- [x] P2-03：定义上下文继承、替换和清除规则，保存每轮结构化请求及变更记录。
- [x] P2-04：增加等待澄清状态，支持暂停、回答后恢复、刷新后恢复交互和失效处理。
- [x] P2-05：前端展示本次分析条件与口径，允许用户检查和修改。

### 约束

存在明确默认口径时使用并展示；关键歧义影响答案时澄清；缺少必需数据时说明无法计算。结构化输出仍需程序验证，不能把格式正确等同于语义正确。

### 验收场景

> 统计去年各地区实付金额 → 只看华东 → 按月拆分 → 改成净销售额。

验证时间和地区继承、分组替换、指标替换、缺失退款数据处理，以及开启新分析时旧条件不会意外污染请求。

**交付物：**指标配置、统一请求契约、会话状态迁移规则、澄清交互、多轮测试。

## 7. 阶段三：Schema 与业务知识 RAG

### 任务

- [x] P3-01：分别管理结构知识与业务知识；前者包括表字段和关联，后者包括指标定义、术语、枚举和限制。
- [x] P3-02：在现有混合检索上比较关键词、向量与融合方案，按验证集选择参数。
- [x] P3-03：命中表字段后补全必要关联路径，处理同名字段与歧义。
- [x] P3-04：记录知识来源、版本、适用数据源和权限范围；更新后正确刷新或失效索引。
- [x] P3-05：检索层实施权限过滤；样例 SQL 仅作参考，必须重新校验当前条件。
- [x] P3-06：接入第二套不同 Schema 的业务数据，先使用同一种数据库验证迁移能力。

### 验收

- 分别报告表／字段召回、关联路径覆盖、检索耗时和下游答案正确率。
- 在未参与调参的题目上比较方案，保留没有改善的结果。
- 第二套数据通过配置和知识导入接入，记录仍需修改的业务代码，不能伪称完全通用。
- 无权限知识不会进入模型上下文；过期知识与新版本冲突有明确处理规则。

**交付物：**知识导入与更新流程、两套演示数据、独立检索评测及失败样本。

## 8. 阶段四：SQL 校验与事实证据链

### 任务

- [x] P4-01：完善只读、表权限、超时、行数限制及参数处理等执行边界。
- [x] P4-02：对支持的查询类型校验指标、筛选、时间和结构化请求的一致性。
- [x] P4-03：针对一对多关联重复计数、聚合粒度、空值、金额单位等风险建立检查与测试。
- [x] P4-04：扩展 EvidenceBundle，使关键事实关联指标版本、查询结果和计算步骤。
- [x] P4-05：报告生成后程序校验数值、名称、期间、排序和引用，明确支持校验的事实类型。
- [x] P4-06：前端提供结论到指标、结果、SQL、来源及限制的查看路径。

### 验收

用可手算的小数据集覆盖跨年、退款、重名客户、一对多关联、空结果和缺失字段。展示错误检测、无法验证与成功验证三类结果；运行时没有标准答案时不得展示虚假的“已证明正确”。

**交付物：**分层校验器、事实引用结构、证据界面、报告错误回归集。

### 指标

| 范围 | 指标 |
|---|---|
| 检索 | 表／字段召回率、关联路径覆盖 |

## 12. 推荐执行顺序与完成标准

推荐主线：

> 可靠性修复 → 业务语义与多轮状态 → RAG 泛化 → 证据校验 → 评测对照 → 运行工程 → 展示交付。

任务状态使用：`待处理 → 实施中 → 待验收 → 已完成`；外部条件不足时记录具体阻塞与已完成部分。仅完成代码不能标为已验收。

每阶段完成需要：

1. 功能或修复可运行。
2. 关键行为有验证结果。
3. 文档与当前实现一致。
4. 限制、风险与未验证项明确。
5. 不破坏已确认的旧功能，必要兼容性变更有说明。

建议后续创建 `docs/UPGRADE_PROGRESS.md` 记录任务编号、改动文件、验证命令、结果及下一步。本文件保留总体方案，实施细节随代码证据调整。

## 13. 给接手模型的首轮工作指令

用户切换模型并要求开始实施后，按以下步骤推进：

1. 阅读本文件和适用的仓库指令，检查 Git 状态，不覆盖现有未提交改动。
2. 阅读历史优化清单及当前关键代码，区分历史问题、仍存在的问题和已完成能力。
3. 建立当前测试与前端构建基线；检查依赖和服务需求，不泄露环境变量或密钥。
4. 创建进度记录，先处理认证、数据隔离、条件丢失、任务终态等高优先级问题。
5. 对每个确认缺陷补充最小有效复现，再实现修复并执行相关回归。
6. 汇报已完成内容、验证证据、未验证边界和下一阶段工作。不要只重复输出宏观方案。

不要未经核验就将所有阶段同时重写；不要为了架构名词而更换整套框架；不要重新开始面试提问。需要产品选择或真实模型预算等无法自行判断的信息时，集中提出少量必要问题，同时继续独立工作。

### 用户可直接发送的交接提示

> 请阅读 `docs/PROJECT_UPGRADE_PLAN.md`，按该方案升级项目。先检查仓库指令、现有代码和未提交修改，建立测试基线并复核 `README_OPTIMIZATION.md`。从阶段一的可靠性问题开始实施，维护 `docs/UPGRADE_PROGRESS.md`，每阶段提供实际验证结果及未完成项。保留现有成果，不要重新做一轮宏观规划，也不要进行面试训练。涉及收费服务、大规模真实模型评测或外网发布时，先明确必要条件与费用或权限。
