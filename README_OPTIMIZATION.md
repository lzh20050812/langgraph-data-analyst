## 1. 文档目的与总体判断

项目已经具备数据清洗、Schema 检索、SQL 生成与修正、分析预测、报告图表、身份管理和异步任务等完整组成部分。下一阶段应优先提高分析结果的正确性、权限边界和异常恢复能力。

当前主要问题是：用户指定的条件可能在节点间丢失，报告展示可能改变预测含义，认证模式组合和任务状态转换仍存在确定缺陷。继续增加页面、Agent 或模型之前，应先让现有能力可验证、可解释、可恢复。

本文是基于本次审查形成的完整工作清单，不宣称已经发现项目中的全部缺陷。优化时发现的新问题应新增编号，保留复现条件和验证记录。

需要保留的设计：

- LangGraph 条件路由与按需调用工具。
- SQL AST 校验、表白名单、数据库只读账号和执行限制。
- `TaskPlan`、`EvidenceBundle`、任务事件和结果持久化。
- 事务化幂等、限流、密码哈希和会话令牌哈希。
- 验证集与测试集分离、公开负结果、保留冻结实验快照。
- 缓存演示明确标注“不调用 LLM”，以及结果中的 SQL 和来源展示。

### 1.2 优先级、证据与状态

| 标记 | 含义 |
|---|---|
| P0 | 最高优先级：认证绕过；对外开放前必须修复 |
| P1 | 高优先级：越权、错误业务结果、任务状态或证据不可靠 |
| P2 | 中优先级：使用流程、评测一致性、维护和验证不足 |
| P3 | 条件性改进：需由实际负载或需求证明收益，当前不单独立项 |
| R | 已通过隔离调用或临时数据库复现 |
| S | 根据当前代码确认，尚未进行真实服务或浏览器复现 |
| D | 设计局限或改进建议，不能当作已发生的运行故障 |

任务状态统一使用：`待处理 → 实施中 → 待验收 → 已完成`。缺少必要数据时标记 `待数据` 并写明缺口；不能为了勾选完成而编造数据或改变验收口径。

## 3. 身份认证与访问边界

### SEC-01：禁止关闭认证机制时通过该凭证获得管理员权限

**位置：** [api/auth.py](api/auth.py) 的 `authenticate_api_key`；[api/main.py](api/main.py) 的 `optional_api_key_auth`；[config/settings.py](config/settings.py)。

**当前问题：** 中间件优先处理任意非空 `X-API-Key`。当 `API_AUTH_ENABLED=False` 时，验证函数直接返回 `LOCAL_PRINCIPAL`。源码默认同时启用网页登录，因此假 Key 可以绕过浏览器会话。这里描述源码默认组合，未读取实际 `.env`。

**实施要求：**

1. 集中定义认证模式及解析顺序。只有显式开放本地模式才允许本地身份回退。
2. 关闭 API Key 认证意味着该机制不接受身份认证，不能返回管理员。
3. 同时存在 cookie 和 Key 时，明确无效 Key 是拒绝请求还是忽略后走有效会话，并用测试固定；两种策略都不得提权。
4. 管理员权限只能来自已经验证的身份，受保护接口不能补一个默认管理员。

**验收：**

- [ ] 网页登录开启、API 认证关闭时，无会话加任意假 Key 仍返回 401。
- [ ] 有效普通用户会话不会因添加假 Key 变为管理员。
- [ ] API 模式中的缺失、错误、有效 Key 分别得到预期结果。
- [ ] 混合认证和显式开放本地模式均有独立测试，管理接口权限一致。

### SEC-02：结果归属与认证方式解耦

**位置：** [api/main.py](api/main.py) 的 `handle_query`、`_get_request_state`；[api/result_store.py](api/result_store.py)。

**当前问题：** `/query` 只在 API 认证开启时写 `_owner_id`；读取时缺失 owner 就跳过归属检查。仅网页登录时，知道他人 `request_id` 的分析员可能读取其报告和图表。

**实施要求：** 始终从已解析的 `Principal` 写入 owner；报告、图表、任务、事件、检查点采用一致的访问策略。历史无 owner 结果应过期、限制为管理员可见或经过明确迁移，不得默认共享。

**验收：**

- [ ] A 用户创建结果后，B 用户即使知道 ID 也无法读取。
- [ ] 同一用例覆盖网页登录、API Key 和混合模式。
- [ ] 管理员访问策略明确，历史缺 owner 记录行为有测试。

### SEC-03：历史记忆隔离与租户定义

**位置：** [storage/chromadb/analysis_memory.py](storage/chromadb/analysis_memory.py)、[agents/report_agent.py](agents/report_agent.py)、[agents/run_context.py](agents/run_context.py)。

**当前问题：** 历史报告写入同一个 collection；元数据缺少 owner/tenant，召回不附带权限过滤。提示词中的“只复用方法”不能阻止其他用户的报告进入模型上下文。

**实施要求：**

1. 本阶段先实现用户级记忆隔离，沿 API、任务、运行上下文传递 owner。
2. `remember/recall` 必须携带作用域；元数据过滤或分区在检索层执行。
3. 明确当前 `Principal.subject` 是用户标识；若未来引入组织租户，另设 `tenant_id`，不要把用户隔离等同于业务数据多租户。
4. 管理员查看运维状态不自动意味着普通分析任务可跨租户召回内容。
5. 旧的无归属记忆隔离处理；缺少隔离能力时关闭复用并给出降级信息。

**验收：**

- [ ] A 写入唯一标记报告，B 的召回及最终模型输入均不包含该标记。
- [ ] 缺失作用域不会退回全局搜索；旧记忆不被普通用户默认读到。
- [ ] 明确当前业务表是共享演示数据还是按租户隔离，文档与实现相符。

## 4. 查询语义与证据传递

### SEM-01：语义配方必须表达整个请求

**位置：** [agents/business_semantics.py](agents/business_semantics.py)、[agents/task_planning.py](agents/task_planning.py)、[agents/sql_agent.py](agents/sql_agent.py)。

**当前问题：** 多个配方匹配到关键词后生成固定 SQL，未处理用户附加的地区、时间、人群等条件。会员分布的“全部客户”和“只统计美国客户”已经复现生成同一 SQL。

**实施要求：**

1. 将指标、维度、时间字段、起止时间、地区、人群、排序和数量限制结构化。
2. 配方声明可表达的条件；只有整个请求都能表达时才命中。
3. 不支持的条件退回受约束 SQL 生成，或明确返回能力不足；不能静默忽略。
4. 使用受控 SQL 构造及参数绑定，禁止直接拼接用户条件字符串。
5. 区分订单时间、注册时间、累计消费口径。数据没有对应时间事实时不能强行给出期间指标。
6. 结果校验同时检查口径和条件，不能只检查输出列名。

**验收：**

- [ ] 构造至少两个国家的最小数据集，全量与美国限定结果按预期不同。
- [ ] 同一问题增加年份、排除条件、Top-N 后，SQL 与结果均遵守条件。
- [ ] 对无法按指定期间计算的客户累计指标，明确说明限制或请求澄清。
- [ ] 使用未参与配方开发的新表达验证，不能仅检查原题和同义词命中。

### SEM-02：专用工具共享明确的数据范围

**位置：** [agents/task_planning.py](agents/task_planning.py) 的 `deterministic_evidence_sql`；[agents/analysis_agent.py](agents/analysis_agent.py)；[agents/prediction_agent.py](agents/prediction_agent.py)。

**当前问题：** RFM、聚类重新读取全体客户；流失特征和运营指标也有独立全表查询。上游即使生成了范围正确的查询，下游仍可能扩大人群。专用证据 SQL 的全量行为已用纯函数确认。

**实施要求：** 专用工具消费带作用域的数据集；确需补查特征时使用同一人群及时间规则，并把新增查询加入证据。区分“训练总体”与“本次评分对象”：模型可在经授权的更大训练集拟合，但报告和名单必须遵守用户请求的对象范围。

**验收：**

- [ ] “仅美国客户做 RFM/聚类”的统计与名单不含其他国家。
- [ ] 混合分析的 SQL 摘要、分群、预测和报告能够对应同一请求范围。
- [ ] 多次读取的来源、版本、范围有记录；不得仅因放进证据包就标记为同源。
- [ ] 结果行数上限导致数据截断时，工具能够识别并拒绝把截断样本当作全量。

### SEM-03：强化跨节点契约和来源信息

**位置：** [agents/contracts.py](agents/contracts.py)、[agents/evidence.py](agents/evidence.py)、[agents/state.py](agents/state.py)。

**当前问题：** 已有 Pydantic 外层契约，但 filters、工具结果等仍主要是任意字典；`update_evidence` 直接更新，未再次验证。证据行数相符也不能证明业务范围相符。

**建议字段（待设计实现，当前 API 尚不保证提供）：**

| 对象 | 建议补充 | 用途 |
|---|---|---|
| 任务范围 | 请求范围、实际生效范围、未支持条件、指标口径 | 检查用户条件是否执行 |
| 数据来源 | 来源 ID、查询/参数、快照标识、数据截止时间、是否截断 | 区分不同工具的数据依据 |
| 分析结果 | 工具名、参数、样本数、来源 ID | 复现统计与分群 |
| 预测结果 | 模型名、训练/验证/测试窗口、phase、评分范围 | 区分历史评估与未来结果 |
| 报告事实 | 事实 ID、值、单位、时间范围、来源 ID | 支持结论引用与核验 |

采用分阶段兼容迁移；大数据集可以使用数据引用和摘要，不必在每个节点复制全部数据。字段和工具枚举需与现有运行状态扩展兼容。

**验收：**

- [ ] 错误工具名、非法范围、来源缺失在边界处被发现。
- [ ] 更新证据后仍验证关键不变量，并区分完整结果与检查点截断视图。
- [ ] SQL、分析、预测、图表、报告可追溯到各自的实际来源。

## 5. 报告正确性

### REP-01：直接消费模型名称和预测阶段

**位置：** [config/prompts/report_prompt.py](config/prompts/report_prompt.py) 的 `_format_prediction_for_prompt`；[agents/prediction_agent.py](agents/prediction_agent.py)。

**当前问题：** 标题写死 XGBoost/Prophet；未来摘要使用 `ds > "2026"`，忽略已有的 `phase`，把回测混入未来。

**实施要求：** 使用预测输出的实际模型字段，按 `phase == "future"` 取未来结果，按 `backtest` 展示回测。日期仅用于排序和显示；无未来结果时明确说明。基线若没有有效预测区间，应标注“未提供区间”，不能把上下界相等解释为确定无误。

**验收：**

- [ ] 分别构造 LogisticRegression、XGBoost、LastValue、Prophet 结果，标题均正确。
- [ ] 2026 年回测、其他年份未来预测及跨年数据均按 phase 正确分组。
- [ ] 摘要条数限制不挤占真实未来月份，缺少阶段标记的旧结果有明确兼容策略。

### REP-02：结论可引用，推测和目标明确标注

**位置：** [agents/report_agent.py](agents/report_agent.py)、[config/prompts/report_prompt.py](config/prompts/report_prompt.py)、[frontend/src/components/StructuredReport.vue](frontend/src/components/StructuredReport.vue)。

**当前局限：** 报告约束主要依赖提示词和长度检查。模板同时要求根因解释、量化预期效果；当前代码不能保证生成内容都获得证据支持。这是缺少验证机制，不代表本次已观察到某份真实报告编造结论。

**实施要求：**

1. 上游生成带单位、期间、来源 ID 的事实清单，LLM 引用事实 ID。
2. 区分观测事实、相关性、待验证假设、建议目标；没有因果证据时不得写成确定根因。
3. 没有干预实验或业务依据时，改善幅度只能作为建议目标，不能写成保证效果。
4. 检查报告引用的关键数值、单位与时间范围；容许明确的舍入和已记录计算。
5. 校验失败时有限次数修正，或降级为确定性摘要并列出未验证内容。

**验收：**

- [ ] 人为注入错误金额、错误单位、历史数字与虚构改善幅度，能够识别或降级。
- [ ] 报告中的关键指标可在界面定位到对应证据。
- [ ] 缺失证据和空数据时不生成确定性根因或虚构指标。

## 6. 任务运行与可观测性

### RUN-01：正确取消未执行任务

**位置：** [api/task_runtime.py](api/task_runtime.py) 的 `cancel`；[api/task_store.py](api/task_store.py) 的 `claim_next`、`recover_expired_leases`。

**当前问题：** 排队任务被改成 `cancelling`，Worker 仅领取 `queued`，租约恢复又要求非空租约，因而无人完成取消。

**实施要求：** 未领取任务在事务内直接 `queued → cancelled`；已领取任务 `running → cancelling → cancelled`。取消与领取的竞争使用条件更新判定，以数据库实际状态为准。重复取消保持幂等，不能覆盖已完成结果。

**验收：**

- [ ] embedded/external 两种模式的排队任务都能取消并到达终态。
- [ ] 取消与领取并发时不存在永久停滞或重复终态事件。
- [ ] 运行中取消在可协作的节点边界生效；UI 不承诺立即中断所有外部调用。

### RUN-02：每次执行都校验租约归属

**位置：** [api/task_runtime.py](api/task_runtime.py) 的 `_execute`；[api/task_store.py](api/task_store.py) 的 `finalize`、`renew_lease`。

**当前问题：** 续租失败被忽略，finalize 仅按 task ID 更新。旧执行失去租约后仍能写入旧结果，清除新 Worker 的归属。

**实施要求：**

1. 每次领取生成单调执行版本或唯一 execution token，不能只依赖可复用 Worker ID。
2. 状态、事件、检查点、最终结果和对话回填都携带并验证执行版本。
3. 续租失败停止接受该执行的新写入，并在可停止边界终止后续工作。
4. 校验归属、更新结果和写终态事件在同一事务完成；拒绝旧写入不能留下伪成功事件。
5. 重试保持明确的至少一次执行语义，避免未经证明就宣称外部调用恰好执行一次。

**验收：**

- [ ] 旧租约过期、新执行接管后，旧执行无法写事件、检查点、结果或对话消息。
- [ ] 同一 Worker ID 再次领取也能拒绝上一版本的写入。
- [ ] 接管、取消、重试和完成竞争时只有合法当前执行能提交结果。

### RUN-03：节点只提交必要增量

**位置：** [agents/state.py](agents/state.py) 的 `messages`；[agents/observability.py](agents/observability.py)；各 Agent 节点。

**当前问题：** 追加型 reducer 与全历史消息返回组合导致重复累加。最小四节点复现中消息从预期 5 条变成 46 条。

**实施要求：** 统一节点更新方式：追加字段仅返回新增内容，或改为明确的替换语义；不能混用。审计其他可变列表、原地修改与检查点快照，避免后续节点改变已有记录。

**验收：**

- [ ] 最小四节点用例严格保留初始化 1 条和每节点 1 条消息。
- [ ] 完整成功、失败和重试路径日志数量随实际事件增加，不重复整段历史。
- [ ] 检查点与审计事件稳定，不受后续列表修改影响。

### RUN-04：节点状态与业务结果一致

**位置：** [agents/observability.py](agents/observability.py)、[agents/contracts.py](agents/contracts.py)、[agents/run_context.py](agents/run_context.py)。

**当前问题：** 返回 `state.error` 的节点仍标记 completed；保存检查点也没有明确区分成功结果与失败诊断。

**实施要求：** 明确 completed、failed、cancelled 的事件规则。允许保存失败诊断，但将“最后成功检查点”和“失败现场快照”分开命名；如仅记录观测快照，不宣称能从该点恢复执行。

**验收：**

- [ ] 抛异常和返回业务错误两种路径都显示 failed。
- [ ] 取消不会显示为业务成功，耗时和已执行节点仍可查看。
- [ ] 任务终态、SSE、数据库事件和前端状态一致。

- [ ] 任务执行时刷新页面，后续结果无需手动再发送问题即可出现。

**验收：**

**验收：**

- [ ] 聊天结果和任务详情都能看到同一套模型证据。

## 8. 算法与数据边界

### ML-01：定义流失预警要预测的未来事件

**位置：** [agents/prediction_agent.py](agents/prediction_agent.py) 的 `_build_churn_features`、`train_churn_model`；[storage/chromadb/schema_metadata.py](storage/chromadb/schema_metadata.py)。

**当前局限：** 使用静态 `churned` 标签及全部订单聚合，缺少特征截止日和未来标签窗口；随机划分不能证明提前预警能力。全量重训后又对同一批客户排名，未排除已经流失的客户。

**实施要求：**

1. 定义“截至日期 T 的可用特征 → 后续明确窗口内的流失事件”，窗口由数据和业务定义决定。
2. 聚合只能使用截止日之前可获得的数据；累计字段若无法回溯，不得假定其代表历史时点。
3. 评估采用符合时间关系的划分；同一客户多期样本还需检查窗口重叠与跨分区影响。
4. 运营名单仅对符合条件的未流失/活跃对象评分，保留评分日期及资格规则。
5. 若现有数据无法支持历史时点和未来标签，将能力明确限定为静态标签分类或风险评分演示；记录待补数据，不伪造时间序列。

**验收：**

- [ ] 数据能支持时，特征、标签及分区均可按时间审计。
- [ ] 数据不能支持时，界面和论文不宣称已验证提前预警效果。
- [ ] 运营 Top-N 不包含不符合资格的已流失对象；测试指标来自独立评估分区。

### ML-02：预处理只在训练数据上拟合

**位置：** [agents/prediction_agent.py](agents/prediction_agent.py)。

**当前问题：** 订单特征先用全体样本中位数填补再划分；类别编码和类别权重也在全量数据上计算。验证、测试信息进入了训练准备过程。这里只确认预处理边界问题，不据此断言其对 AUC 的实际影响大小。

**实施要求：** 先划分，再在训练分区拟合缺失填补、编码和类别权重；通过统一 Pipeline/转换器处理验证、测试及未来评分。最终用于运营的全量重训与独立评估指标分开记录。

**验收：**

- [ ] 修改测试集缺失值分布或类别，不改变已拟合训练转换器。
- [ ] 未见类别可以稳定处理，训练与评分特征顺序一致。
- [ ] 评估数据不参与阈值、模型或特征选择。

### ML-03：运行参数与实验参数共享

**位置：** [agents/analysis_agent.py](agents/analysis_agent.py)、[evaluation/experiments/model_experiment_formal.py](evaluation/experiments/model_experiment_formal.py)、[evaluation/final_results/final_metrics.json](evaluation/final_results/final_metrics.json)。

**当前问题：** 冻结实验选择 `k=2`，实际节点仍默认 `k=4`，初始化次数也不同。历史实验成绩不能直接代表当前应用配置。

**实施要求：** 让实验与应用共享特征处理、选参实现或版本化配置。不同数据范围不保证仍以 k=2 最佳；应执行明确选参策略，或解释固定参数的适用范围。

**验收：**

- [ ] 同一快照、配置、随机种子下，两条路径使用相同参数并给出一致结果。
- [ ] UI 显示实际参数和适用样本数；固定 k 与自动选 k 不混称。
- [ ] 对小样本、重复样本、有效簇数不足给出明确错误或降级说明。

| M3：修运行 | RUN-01/02/03/04、UX-03/04 | M1；行为测试先行 | 取消、接管、刷新和故障诊断正确 |

## 12. 本地验证方式



这些是已有测试文件入口，当前通过不代表已经覆盖本文新增验收项。模拟外部依赖时应使用明确的假数据与临时数据库，避免初始化实际运行存储。

### 12.2 前端类型与构建

依赖已经安装时：

全新环境先按锁文件执行 `npm --prefix frontend ci`，该步骤需要获取依赖；build 会更新构建产物。浏览器行为测试的框架和脚本属于 QA-01 待补工作，当前不能假定项目已有可运行的 `npm test` 或 E2E 命令。
