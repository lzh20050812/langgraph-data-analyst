# 阶段六容量与组件决策

> 日期：2026-09-19。以下是本地工程边界，不是生产 SLA。

## 当前结论

任务元数据暂留 SQLite WAL，业务数据继续使用 MySQL；本阶段不引入 Redis、消息队列或 PostgreSQL。原因是当前部署目标为单主机、默认 4 个并发执行槽和 20 个排队任务，已有原子领取、租约、幂等键与持久事件，尚无测得的队列或锁瓶颈。现在同时加入多个重叠组件只会增加恢复路径和运维面。

SQLite 决策仅适用于单主机。若满足任一条件，应迁移任务元数据到 PostgreSQL：需要多主机主动执行、SQLite 写锁进入显著延迟、任务/事件保留规模超过单文件运维能力，或需要数据库级高可用。迁移时必须保留状态机、条件更新、唯一幂等键和执行令牌语义，不能只复制表结构。

只有在确认数据库轮询是主要瓶颈、需要跨主机即时分发或需要独立的延迟/优先级队列后，才引入消息队列。Redis 可作为选定队列的实现或短期缓存，但不应同时承担无法说明一致性边界的“第二任务真相源”。持久任务状态仍应只有一个权威存储。

## 已验证容量边界

- API 层已有历史本地并发探针：1、2、4 Worker 成功率 100%，四 Worker 约 1.392 req/s。该值来自接口/固定负载，不能代表真实模型吞吐。
- 阶段六故障测试使用临时 SQLite，覆盖并发唯一领取、租约交接、旧令牌拒写、幂等重复提交、状态终态和事件一致性。
- Compose 中 App 与 Worker 通过 Docker named volume 共享 SQLite WAL；pytest 使用独立会话临时库。完整 220 项回归与前端构建在容器运行时执行，Worker 重启计数保持 0。
- 真实模型吞吐没有在本阶段压测。模型延迟、提供方限流和 Token 长度会主导端到端容量，不能用无模型测试外推。
- 默认上限：4 个并发、20 个排队、单任务 16 次 LLM 调用、100,000 Token、300 秒、1 美元估算预算；价格默认为 0，部署方必须按实际模型配置。

## 迁移触发测量

后续容量测试应分别记录 API 接收延迟、SQLite 事务等待、领取延迟、事件写入速率、队列深度、模型 P50/P95、Token/任务和成本/任务。只有在分离模型等待后仍观察到持久层或分发瓶颈，才启动组件迁移。真实模型压测需另设费用上限和提供方限流保护。
